## 一、术语与核心定义

| 术语 | 定义 |
|------|------|
| 进食窗口（Eating Window） | 用户方案中允许进食的本地时间段，如 12:00–20:00（D-03 默认窗口表）。窗口**起止以「本地墙钟时间（HH:mm）+ 24h 周期」表达**，落地时换算为 UTC 锚点（见 §3）。 |
| 断食窗口（Fasting Window） | 进食窗口之外的 24h 补集。断食窗口常跨午夜（如 20:00–次日 12:00）。 |
| 断食周期（FastCycle） | 一次断食的完整生命周期实体：从某次进食窗口结束（断食开始）到下一次进食窗口开始（断食结束）。是打卡、达标判定、streak（D-12）的最小单位。 |
| 打卡归属日（Attribution Date） | 一次 FastCycle 计入的自然日。**= 该周期结束时的进食窗口所属自然日**（D-07）。形式化定义见 §3.3。 |
| 达标（Qualified） | 本次 FastCycle 的达标结论，规则见 D-08 与 §5 判定表。 |
| 破窗 | 在进食窗口到点前手动「结束断食」。 |
| 延长（Extend） | 将当前 FastCycle 的计划结束时刻后移，步进 30min，累计上限 4h（D-10）。 |
| 锚点（Anchor） | FastCycle 上的 UTC 时间戳字段，一切计时计算只基于锚点，不基于本地墙钟差值。 |

## 二、状态机

### 2.1 状态枚举

应用级当前状态 `FastingState`（单例，全局唯一当前值）：

| 状态 | 含义 | 计时环展示（设计方案定稿 §4.1） |
|------|------|------|
| `NO_PLAN` | 未启动任何断食方案（新用户未引导/跳过且未兜底前） | 引导启动方案，不显示倒计时 |
| `EATING` | 处于进食窗口内 | 暖阳橙弧（`#FF9F45`），倒计时 = 距进食窗口结束 |
| `FASTING` | 处于断食窗口内，未发生延长 | 轻盈绿弧（`#3DBE8B`），倒计时 = 距计划进食窗口开始 |
| `FASTING_EXTENDED` | 处于断食窗口内，本周期已执行过 ≥1 次延长 | 绿弧 + 「已延长 +N min」徽标，倒计时 = 距延长后的进食窗口开始 |

FastCycle 实体级终态 `CycleResult`（写入 `FastingRecord` 后不可变）：

| 终态 | 含义 | 达标 |
|------|------|------|
| `COMPLETED_ON_TIME` | 进食窗口到点自然开启，完整走完 | ✅ 达标 |
| `COMPLETED_EARLY_PASS` | 手动提前破窗，提前量 ≤15min（D-08） | ✅ 达标 |
| `COMPLETED_EXTENDED` | 延长后走完，实际断食时长 ≥ 计划时长（D-08） | ✅ 达标 |
| `BROKEN_EARLY` | 手动提前破窗，提前量 >15min（D-08） | ❌ 不达标 |
| `MISSED` | 归属日已过但该周期无任何完成/破窗事件（漏打卡，见 §6-B12） | ❌ 不达标 |

> 〔假设〕`NO_PLAN` 是 PRD「跳过问卷→默认 16:8 兜底」（D-03）落地前的瞬态；兜底写入后即转入 `EATING` 或 `FASTING`，正常用户不长期停留。

### 2.2 事件枚举

| 事件 | 触发源 | 说明 |
|------|--------|------|
| `EAT_WINDOW_START_DUE` | 本地通知/前台计时器到点 | 计划（或延长后）的进食窗口开始时刻到达 |
| `EAT_WINDOW_END_DUE` | 本地通知/前台计时器到点 | 进食窗口结束时刻到达（= 新断食开始） |
| `MANUAL_END_FAST` | 用户点「结束断食」 | 仅 `FASTING` / `FASTING_EXTENDED` 下可用 |
| `MANUAL_EXTEND` | 用户点「延长」 | 步进 30min；仅 `FASTING` / `FASTING_EXTENDED` 下可用 |
| `PLAN_CHANGE` | 用户在「我的」更换方案/窗口 | **次日 0:00（本地）生效**（D-06），当日周期不受影响 |
| `TIMEZONE_CHANGE` | 系统时区变化（飞行、手动改时区） | iOS `NSSystemTimeZoneDidChange` / Android `ACTION_TIMEZONE_CHANGED` |
| `CLOCK_CHANGED` | 系统时间被回拨/拨快 | Android `ACTION_TIME_CHANGED`；iOS 无公开回调，前台启动时校时（§4.4） |
| `APP_FOREGROUND` | App 启动/回前台/杀进程重开/设备重启后首开 | **恢复事件**：用锚点重算，不改变业务状态，只修正 UI 与通知 |
| `PLAN_ACTIVATE` | 新方案生效时刻（本地 0:00）到达 | 由 `PLAN_CHANGE` 预排的定时任务触发 |

### 2.3 状态迁移表（当前状态 × 事件 → 下一状态 × 副作用）

| # | 当前状态 | 事件 | 下一状态 | 副作用（必须全部执行） |
|---|----------|------|----------|------------------------|
| T1 | `NO_PLAN` | 方案写入（一键启动/兜底） | `EATING` 或 `FASTING`（按当前时刻落点） | 初始化 FastingPlan；计算当前 FastCycle 锚点；重排本地通知（§7）；刷新小组件 |
| T2 | `FASTING` | `EAT_WINDOW_START_DUE` | `EATING` | 关闭当前 FastCycle → `COMPLETED_ON_TIME`；写 `FastingRecord`（归属日 = 进食窗口自然日）；触发破壳庆祝微交互；streak +1（D-12 口径，交 M5 规格）；按方案排下一个周期锚点；重排通知；刷新小组件 |
| T3 | `FASTING` | `MANUAL_END_FAST`，提前量 ≤15min | `EATING` | 关闭周期 → `COMPLETED_EARLY_PASS`；记录实际断食时长；streak +1；以**实际破窗时刻**作为进食窗口起点重排本日进食结束锚点〔假设：提前破窗不压缩也不后移当日进食结束时刻，仍按计划 20:00 结束〕；重排通知；刷新小组件 |
| T4 | `FASTING` | `MANUAL_END_FAST`，提前量 >15min | `EATING` | 关闭周期 → `BROKEN_EARLY`；记录实际断食时长；streak 归零 + 断签弹窗（三态见 D-12/M5 规格）；进食窗口结束锚点同 T3 处理；重排通知；刷新小组件 |
| T5 | `FASTING` | `MANUAL_EXTEND`（累计延长 <4h） | `FASTING_EXTENDED` | 本周期 `plannedEnd += 30min`（UTC 锚点直接 +1800s）；当日进食窗口整体后移 30min，**进食窗口时长不压缩**（进食结束锚点同步 +30min，D-10）；重排通知；刷新小组件 |
| T6 | `FASTING_EXTENDED` | `MANUAL_EXTEND`（累计 <4h） | `FASTING_EXTENDED` | 同 T5，`extendMinutes` 累加 |
| T7 | `FASTING_EXTENDED` | `MANUAL_EXTEND`（累计已达 4h） | `FASTING_EXTENDED`（不变） | 「延长」按钮置 disabled；提示「单次最多延长 4 小时」（D-10） |
| T8 | `FASTING_EXTENDED` | `EAT_WINDOW_START_DUE`（延长后新锚点到点） | `EATING` | 关闭周期 → `COMPLETED_EXTENDED`（实际时长 ≥ 计划时长必成立）；其余同 T2 |
| T9 | `FASTING_EXTENDED` | `MANUAL_END_FAST`（在延长后锚点之前） | `EATING` | 若实际断食时长 ≥ 原计划时长 → `COMPLETED_EXTENDED`（达标）；否则按提前量走 T3/T4 口径（D-08：「延长后最终断食时长 ≥ 计划时长 → 仍记达标」） |
| T10 | `EATING` | `EAT_WINDOW_END_DUE` | `FASTING` | 开启新 FastCycle（锚点 = 本地 20:00 换算 UTC）；写新周期行；重排通知；刷新小组件 |
| T11 | `EATING` | `MANUAL_END_FAST` / `MANUAL_EXTEND` | `EATING`（不变） | 按钮在进食态不展示/置灰，事件不可达（防御性丢弃） |
| T12 | 任意 | `PLAN_CHANGE` | 当前状态不变 | 确认弹窗明示「新方案将于明日 0:00 生效」（D-06）；写入 pendingPlan（`effectiveDate = 明日`）；当日锚点不动；排 `PLAN_ACTIVATE` 定时任务 |
| T13 | 任意 | `PLAN_ACTIVATE`（本地 0:00 到点） | 按新方案重算后的状态 | pendingPlan 转正；**从今日起的周期按新窗口计算**；已在进行中的当日周期：若当前处于断食中且新窗口使进食开始提前，则以新锚点为准（取「当前时刻之后最近的窗口边界」原则，§4.2 伪代码）；重排通知；刷新小组件 |
| T14 | 任意 | `TIMEZONE_CHANGE` | 状态枚举不变（按新时区重算落点，理论可能翻转 EATING/FASTING，见 §6-B6） | **UTC 锚点全部不变**；用新时区重渲染归属日与窗口墙钟；**重排全部本地通知**（D-09）；刷新小组件；若归属日在新时区下变化，已冻结的历史 `FastingRecord.date` 不改写（§3.3 冻结规则） |
| T15 | 任意 | `CLOCK_CHANGED` | 按真实 UTC now 重算落点 | 以可信时间源校时（§4.4）；重算当前状态与倒计时；重排通知；刷新小组件；异常偏移 >5min 记诊断日志 |
| T16 | 任意 | `APP_FOREGROUND` | 按锚点重算后的状态 | 纯恢复：重算当前状态/倒计时/归属文案；对账通知（补排缺失、清除过期）；刷新小组件。**绝不在恢复路径上补发「到点」事件的业务副作用之外的写入**——若离线期间跨越了窗口边界，按 T2/T10 规则补关闭/补开启周期（见 §6-B11/B12） |

> 状态机的任何迁移都是「读 UTC 锚点 → 纯函数计算 → 写记录 + 重排通知 + 刷小组件」，无隐藏副作用。迁移函数必须是**纯函数 + 全量单测**（对齐评审项 3 对规则引擎的同款要求）。

## 三、计时模型（D-07 落地）

### 3.1 存储与渲染原则

- **存储**：全部锚点为 UTC epoch 秒（`plannedStartUtc`, `plannedEndUtc`, `extendedMinutes`, `actualEndUtc`, `eatWindowEndUtc`）。SQLite（drift，D-17）中存 INTEGER。
- **渲染**：展示层唯一入口 `toLocal(utc, deviceTimeZone)`，禁止在业务逻辑中直接读写 `DateTime.now()` 的本地分量。
- **窗口配置**：FastingPlan 存「本地墙钟表达」（如 `eatStart=12:00, eatEnd=20:00`）+ 生成锚点时的时区 ID；锚点由窗口墙钟 + 时区换算而来。

### 3.2 锚点生成规则

```
# 由方案窗口墙钟生成某日（本地自然日 d）的锚点
function anchorsFor(plan, localDate d, tz):
    eatStartUtc = toUtc(d + plan.eatStart, tz)     # 进食窗口开始
    eatEndUtc   = toUtc(d + plan.eatEnd, tz)       # 进食窗口结束
    if plan.eatEnd <= plan.eatStart:               # 跨午夜进食窗口（MVP 不推荐但防御）
        eatEndUtc += 24h
    return (eatStartUtc, eatEndUtc)
```

断食周期 `FastCycle(n)` 定义为：`[eatEndUtc(d=n-1), eatStartUtc(d=n))`，即「昨晚进食结束 → 今天进食开始」。跨午夜窗口（20:00–次日 12:00）下，断食从 d-1 日 20:00 持续到 d 日 12:00。

### 3.3 打卡归属日的形式化定义（D-07 核心）

**定义**：一次 FastCycle 的打卡归属日 = 结束该周期的**进食窗口开始时刻**在**该时刻设备时区**下渲染出的自然日。

**冻结规则**：归属日在进食窗口开始时刻（周期关闭时）计算并写入 `FastingRecord.date`，**此后不再因时区变化、时间回拨而改写**。周期进行中展示的归属文案是「预计算值」，允许随时区变化实时更新，直至冻结。

```python
# 伪代码：归属日计算与达标判定（Spike 须按此实现并配单测）
def close_cycle(cycle: FastCycle, end_utc: int, tz_at_end: str, reason: str) -> FastingRecord:
    # 1. 归属日 = 进食窗口开始时刻的本地自然日（本次关闭 = 进食窗口开启）
    attribution_date = local_date(end_utc, tz_at_end)          # 如 2026-07-28

    # 2. 实际断食时长
    actual = end_utc - cycle.start_utc                          # 秒
    planned = cycle.planned_end_utc - cycle.start_utc           # 含延长
    planned_original = planned - cycle.extended_minutes * 60    # 原计划时长

    # 3. 达标判定（D-08；tolerance 走服务端配置，默认 900s）
    tolerance = remote_config("fast_tolerance_sec", 900)
    if reason == "WINDOW_START_DUE":
        result, qualified = "COMPLETED_ON_TIME" if cycle.extended_minutes == 0 \
            else "COMPLETED_EXTENDED", True
    elif reason == "MANUAL_END":
        early_by = cycle.planned_end_utc - end_utc              # >0 表示提前
        if cycle.extended_minutes > 0 and actual >= planned_original:
            result, qualified = "COMPLETED_EXTENDED", True      # D-08 延长条款
        elif early_by <= tolerance:
            result, qualified = "COMPLETED_EARLY_PASS", True    # D-08 容差条款
        else:
            result, qualified = "BROKEN_EARLY", False
    return FastingRecord(date=attribution_date, actual_sec=actual,
                         qualified=qualified, result=result)
```

### 3.4 时间读数纪律

- 计时与判定只用单调可信的 UTC now：优先系统 UTC（`DateTime.now().toUtc()` 的 epoch 语义不受时区影响），辅以开机时长（`SystemClock.elapsedRealtime()` / `mach_absolute_time`）做回拨侦测。
- 倒计时显示值 = `anchorUtc − nowUtc`，任何情况下不为负（到点即触发迁移）。

## 四、关键流程规则

### 4.1 方案更换次日生效（D-06）

| 规则 | 内容 |
|------|------|
| 生效时刻 | 本地时区次日 0:00 |
| 当日数据 | 已产生的 FastCycle/FastingRecord 原样保留，不回算 |
| 交互 | 确认弹窗必须明示「新方案将于 X 月 X 日 0:00 生效」 |
| 落地 | pendingPlan + `PLAN_ACTIVATE` 本地定时任务（同时用本地通知触发器兜底，杀进程后仍能于 0:00 后首次启动时由 `APP_FOREGROUND` 对账转正） |

### 4.2 状态落点重算（时区变更/校时/恢复共用）

```python
def resolve_state(now_utc: int, plan, tz: str) -> FastingState:
    # 原则：以「当前时刻之后最近的窗口边界」重建所处区间
    for d in [today_local(now_utc, tz) - 1, today_local(now_utc, tz)]:
        (es, ee) = anchorsFor(plan, d, tz)
        if es <= now_utc < ee:  return EATING(cycle_end=ee)
        if ee <= now_utc < next_es(d+1):  return FASTING(target=next_es)
```

### 4.3 延长规则（D-10）

- 步进固定 30min；**每个 FastCycle 累计延长上限 4h**（即最多 8 次）。〔假设〕D-10「单次最多延长 4 小时」按「单周期累计」理解，待产品确认。
- 延长只后移进食窗口开始锚点与当日进食结束锚点，进食窗口总时长不变（不压缩）。
- 延长不跨周期继承，新周期从 0 重新计数。

### 4.4 系统时间被改的处理（评审项 1 明确点）

| 情形 | 检测 | 处理 |
|------|------|------|
| 回拨（now 变小） | 持久化的 `lastSeenUtc` > now → 判定回拨 | 不回滚任何已冻结记录；`lastSeenUtc` 不后退；倒计时按锚点自然变长，UI 如实展示；不惩罚、不判破窗 |
| 拨快（now 变大） | 偏移 >5min 记诊断 | 按真实 now 重算落点；若因此跨过窗口边界，按正常迁移补关闭周期——拨快导致「跳过」进食开始点的，按 `COMPLETED_ON_TIME` 关闭并提示归属日〔待外部确认：是否需防作弊策略，MVP 不做反作弊，仅记录〕 |
| 时区被手动改 | 同 `TIMEZONE_CHANGE` | 走 T14 |

## 五、达标判定汇总表（D-08）

| 情形 | 结果枚举 | 达标 | streak（D-12） |
|------|----------|------|----------------|
| 进食窗口到点自然开启（未延长） | `COMPLETED_ON_TIME` | ✅ | +1 |

## 六、边界用例表（Spike 验收用例，全部需自动化测试覆盖）

> 时间线约定：`BJT` = Asia/Shanghai（UTC+8）；无特殊说明默认方案 16:8（进食 12:00–20:00），容差 15min。

| # | 场景 | 输入时间线 | 预期状态/归属日/达标判定 |
|---|------|-----------|--------------------------|
| B1 | 跨午夜窗口（常规日） | d 日 20:00 进食结束（断食开始）→ d+1 日 12:00 进食窗口到点 | d 日 20:00 → `FASTING`；d+1 日 12:00 → `EATING`；周期关闭 `COMPLETED_ON_TIME`；**归属日 = d+1**；✅ 达标。计时环在 d 日 23:59→d+1 日 00:00 无跳变 |
| B2 | 提前结束 ≤15min | 断食中，d+1 日 11:46 手动「结束断食」（提前 14min） | `COMPLETED_EARLY_PASS`；归属日 d+1；✅ 达标；streak +1 |
| B3 | 提前结束 >15min | d+1 日 11:44 手动结束（提前 16min） | `BROKEN_EARLY`；归属日 d+1；❌ 不达标；streak 归零 + 断签弹窗（三态：可补签/已用尽/已断签，D-12） |

## 七、本地通知调度规则（D-09）

### 7.1 通知排程表

| 通知 | 触发时刻（锚点换算） | 默认文案（中英双语，i18n key，D-15） |
|------|----------------------|--------------------------------------|
| `notify_eat_soon` | 进食窗口开始 −15min（提前量设置可调，默认 15） | 「还有 15 分钟就可以进食啦」/ "Eating window opens in 15 min" |
| `notify_eat_start` | 进食窗口开始（含延长后新锚点） | 「可以进食啦，本次断食计入 X 月 X 日 ✅」 |
| `notify_fast_start` | 进食窗口结束（= 断食开始）到点 | 「断食窗口开始啦，今天也很棒，加油坚持～」（对齐设计稿品牌语气） |

### 7.2 调度规则

1. **实现**：`flutter_local_notifications`（D-17），`zonedSchedule` + 设备时区；纯本地通知，不依赖 APNs/FCM/厂商推送通道在线。
2. **排程窗口**：每次重排为未来 48h 内全部触发点（每周期 3 条 × 2 天 ≈ 6 条，远低于 iOS 64 条上限）。
3. **重排触发器**（任一发生即全量重排）：任何状态迁移副作用、时区变更（T14）、校时偏移（T15）、方案生效（T13）、App 前台（对账补排）、Android 设备重启（BOOT_COMPLETED）。
4. **权限**：用户关闭通知权限 → 不阻断计时，App 内顶部横幅引导开启（PRD M2）；尊重系统勿扰。
5. **过期清理**：重排前先 `cancelAll()` 再重建，避免时区变化后旧通知在错误时刻触发。

## 八、双端实现要点（小组件倒计时同步误差 ≤1 分钟）

**同步总原则（双端一致）**：小组件**不传输「剩余时间数值」**，只传输**目标锚点 UTC + 状态枚举**（经 App Group / SharedPreferences 共享容器，`home_widget` + 原生桥，D-17）；倒计时由小组件侧的系统级活控件实时渲染，天然零漂移。App 内与小组件读同一锚点 → 误差来源只剩小组件刷新延迟，可稳定 ≤1 分钟。

### 8.1 iOS

| 能力 | 方案 |
|------|------|
| 锁屏/桌面小组件（iOS 15+，D-14） | WidgetKit `TimelineProvider`：每次状态变化/前台/锚点变化时 `reloadAllTimelines()`，写入共享锚点；**倒计时用 SwiftUI `Text(timerInterval:)` 渲染**（系统按秒自刷新，无需 timeline 条目逐分钟刷新） |
| Live Activity（iOS 16.1+ 增强项） | ActivityKit 启动断食 Live Activity，灵动岛/锁屏实时倒计时；状态迁移时 `update`，周期关闭时 `end`。**不依赖 APNs 更新通道，本地更新即可**（无推送依赖） |
| 降级方案（iOS 15.x–16.0） | 无 Live Activity → 仅 WidgetKit 小组件 + 本地通知；功能不阻断（D-14：Live Activity 为增强项） |
| 后台刷新 | `BGAppRefreshTask`（BGTaskScheduler）注册周期性对账任务：重算状态、刷新 timeline、补排通知；系统调度不保证精确时刻，**精确到点依靠本地通知 + 锚点渲染，不依靠 BGTask** |
| 时区/时间变化 | `NSSystemTimeZoneDidChangeNotification` → 走 T14；回前台统一校时 |

### 8.2 Android

| 能力 | 方案 |
|------|------|
| 桌面小组件（API 26+） | AppWidget `RemoteViews`：倒计时用 **`Chronometer`（`setCountDown(true)`，`setBase(anchorElapsedRealtime)`）**，系统侧自渲染；锚点经 `home_widget` SharedPreferences 写入 |
| 状态同步 | 状态迁移/锚点变化时 `AppWidgetManager.notifyAppWidgetViewDataChanged` / `updateAppWidget`；App 前台时顺带刷新 |
| 后台任务 | WorkManager：① 周期对账任务（重排通知、刷小组件）；② `BOOT_COMPLETED` 接收器登记一次性任务（B14） |
| 精确提醒 | 本地通知触发用 `setExactAndAllowWhileIdle` + `SCHEDULE_EXACT_ALARM`（API 31+ 需运行时检查，被回收时引导重授权） |
| 厂商通道限制（小米/华为/OPPO/vivo 等） | **本地通知与小组件不依赖厂商推送通道**；风险点是 OEM 杀后台导致 WorkManager/精确闹钟延迟：落地措施 = 首次启动引导开启「自启动/无限制电池优化」白名单（各厂商 intent 跳转）；通知未送达不阻断计时（锚点模型保证重开即正确）〔待外部确认：聚合推送 SDK（个推/极光，D-17）是否用于 M2 提醒增强，MVP 判定为不需要〕 |

### 8.3 同步误差验收方法

- 自动化：同一锚点下，App 内倒计时读数与小组件渲染读数在任意采样点差值 ≤60s（真机 + 模拟器双端各跑 B1/B5/B8 场景）。
- 设计预期：因双端均渲染「锚点 − now」，稳态误差 ≈0；误差上限 60s 用于覆盖小组件刷新节流。
