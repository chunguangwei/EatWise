## 1. 四态持久化模型

### 1.1 四态定义

每条本地记录（FoodEntry / FastingRecord / User 资料 / FastingPlan）在本地库中携带 `syncStatus` 字段，取值与含义如下：

| 状态 | 枚举值 | 含义 | 用户可见性 |
|------|--------|------|-----------|
| 提交中 | `submitting` | 乐观更新已入账，上行请求在途（含撤销 10 秒窗内的待上行期，D-11） | 列表正常展示，「已记录·撤销」吐司展示中 |
| 已同步 | `synced` | 服务端已确认入库，本地持有服务端版本号与时间戳 | 默认无感 |
| 待同步 | `pending` | 上行失败（网络/5xx/离线写入）待重试 | 计入「待同步 N 条」入口（第 4 章） |
| 冲突 | `conflicted` | 上行时版本/etag 不匹配，自动合并未完全覆盖，需人工处理 | 进入冲突队列，冲突入口红点提示 |

关键不变式：**任何状态下记录都不丢**；用户关闭 App、断网、杀进程后状态可恢复（状态落本地库而非内存）。

### 1.2 本地记录同步字段

所有四态实体在本地表中统一携带：

| 字段 | 类型 | 说明 |
|------|------|------|
| `localId` | TEXT (UUIDv4) | 本地主键，客户端生成，全生命周期不变 |
| `serverId` | TEXT NULL | 服务端分配主键，首次同步成功后回填 |
| `clientRequestId` | TEXT (UUIDv4) | 幂等键，每次上行操作生成（create/update/delete 各一个），见 2.2 |
| `syncStatus` | TEXT | 四态之一 |
| `localVersion` | INT | 本地每次修改 +1 |
| `serverVersion` | INT NULL | 最近一次同步成功的服务端版本号（etag 语义） |
| `serverUpdatedAt` | TEXT NULL | 最近一次同步成功的服务端时间戳（UTC，D-07），LWW 仲裁依据 |
| `retryCount` | INT | 连续重试次数，用于退避计算（4.2） |
| `lastError` | TEXT NULL | 最近一次失败原因码（供调试与告警埋点） |
| `deleted` | INT (0/1) | 本地软删标记（tombstone），删除也要上行 |

### 1.3 状态迁移表（核心）

| # | 当前状态 | 触发事件 | 动作 | 下一状态 | 备注 |
|---|----------|----------|------|----------|------|
| T1 | —（新建） | 在线：用户确认记录 | 乐观更新入账（UI 立即展示）→ 写本地库 `submitting`，生成 `clientRequestId`，启动撤销 10 秒窗（D-11） | `submitting` | 撤销窗内暂不发出上行请求〔假设：撤销窗结束才发请求，避免「已上行又撤销」的删除往返〕 |
| T2 | —（新建） | 离线：用户确认记录 | 乐观更新入账 → 写本地库 `pending`；撤销窗仍然生效 | `pending` | 离线也允许撤销（纯本地回滚） |
| T3 | `submitting` | 撤销窗内点击「撤销」（D-11，10 秒） | 本地删除该条（乐观更新回滚），取消待发请求 | —（记录移除） | 请求未发出则零网络成本；若请求已发出（如撤销窗期间用户重复编辑触发提前上行〔假设〕）→ 转 T9 删除上行 |
| T4 | `submitting` | 撤销窗结束，上行请求成功（2xx） | 回填 `serverId` / `serverVersion` / `serverUpdatedAt`，`retryCount=0` | `synced` | 服务端幂等去重（2.2），重复提交不产生重复记录 |
| T5 | `submitting` | 上行失败：网络错误 / 5xx / 429 | 转 `pending`，`retryCount+1`，进入退避重试队列（4.2） | `pending` | 用户数据仍在，UI 无回滚（与 PRD「失败则回滚」的差异说明：乐观更新不回滚已确认入账的数据，仅在提交校验失败时回滚，见 1.4） |
| T6 | `submitting` | 上行返回 409（版本冲突） | 拉取服务端版本 → 走字段级合并（第 3 章）；可自动合并则合并后重发 | `submitting`（重发）或 `conflicted` | 存在不可合并字段时转 `conflicted` |
| T7 | `submitting` | 上行返回 4xx（非 409，校验拒绝） | 回滚乐观更新（UI 移除该条），本地标记 `lastError`，Toast 提示「该条记录未被保存」 | —（记录移除） | 防腐层拒绝（第 5 章），不重试；记录原文进本地死信封存 7 天供排查〔假设〕 |
| T8 | `pending` | 网络恢复 / 退避到期 | 批量上行（2.3），成功回填 | `synced` | 失败继续 `pending`，`retryCount+1` |
| T9 | `synced` | 用户编辑 / 删除该条 | 本地先改，`localVersion+1`，重新生成 `clientRequestId`；删除置 `deleted=1` | `submitting` | 删除同样走撤销 10 秒窗（D-11 适用所有变更〔假设〕） |
| T10 | `pending` | 用户再次编辑 | 本地直接改，`localVersion+1`，保留 `pending`；上行时携带最新值 | `pending` | 不需要先同步再改 |
| T11 | `pending` | 上行返回 409 且含不可合并字段 | 本地快照入冲突队列（保留本机版 + 拉取服务端版双份） | `conflicted` | 见第 3 章 |
| T12 | `conflicted` | 用户在冲突界面选择「保留本机」 | 以本机版强制覆盖上行（`forceOverwrite=1` + 最新 `serverVersion`） | `submitting` → `synced` | 服务端记录 `overriddenBy=user_choice` 审计日志〔假设〕 |
| T13 | `conflicted` | 用户选择「保留云端」 | 丢弃本机版，写入服务端版 | `synced` | 本机版存入本地回收站 30 天〔假设〕，可在冲突界面恢复 |
| T14 | `conflicted` | 用户选择「合并可合并字段」 | 可合并字段按 LWW 合成，不可合并字段取用户逐项选择值，然后上行 | `submitting` → `synced` | 仅当实体存在 ≥1 个可 LWW 字段时提供 |
| T15 | 任意非 `synced` | 退出登录 | 本地库按 `userId` 隔离保留，未同步数据**不随登出清除** | 不变 | 见 1.5 重登规则 |
| T16 | 任意 | 重新登录（同账号） | 恢复该 `userId` 本地数据；`pending`/`conflicted` 继续走原队列 | 不变 | — |
| T17 | 任意 | 重新登录（异账号） | 先弹窗提示旧账号存在 N 条未同步记录：「先同步」/「放弃」；选择后切换命名空间 | 视选择 | 放弃 → 旧数据进入 30 天回收站后物理删除〔假设〕 |
| T18 | — | 未登录状态下记录 | 绑定 `localUserId=anonymous`；首次登录成功后全部迁移到新 `userId` 并置 `pending` 批量上行 | `pending` | 与 D-13 登录方式无关，匿名数据归属迁移为一次性操作 |

### 1.4 乐观更新与回滚边界（对齐 PRD M3 与 D-20）

- PRD 所述「失败则回滚」细化为两类失败：
  - **可重试失败**（网络/5xx/429）：不回滚，转 `pending` 保数据——这是 D-20 四态模型的核心目的（评审项 4：吐司消失后用户仍能确认是否入库）。
  - **不可重试失败**（4xx 校验拒绝）：回滚 + 明确提示，因为继续保留必然永远无法入库。
- 撤销窗（D-11，10 秒）内数据状态为 `submitting`，用户感知与 PRD/设计稿「已记录·撤销」吐司一致；撤销窗结束、上行在途期间吐司已消失，此时记录状态可通过「待同步 N 条」入口查证（第 4 章）。

### 1.5 重登与多账号规则汇总

| 场景 | 规则 |
|------|------|
| 同账号重登 | 本地数据原样保留，`pending`/`conflicted` 队列继续（T16） |
| 异账号登录 | 强制先处理旧账号未同步数据（T17），禁止静默丢弃 |
| 卸载重装 | 本地库销毁，全部数据以云端增量下行恢复（2.4）；未同步的 `pending`/`conflicted` 数据丢失——登录态下在「我的 → 数据与同步」页对存在未同步数据的账号给出「卸载前请先同步」提示〔假设〕 |
| 服务端数据清除（用户行使删除权，D-18） | 云端下发 `accountPurged` 标记，客户端清空本地库并回到引导页 |

## 2. 同步协议

### 2.1 总览

- 架构：**本地优先（offline-first）**。所有读写先落 SQLite（drift），同步引擎异步与云端 PostgreSQL 对账（D-17、D-20）。
- 时间戳：全部 **UTC 存储**，渲染按设备本地时区换算（D-07）。LWW 仲裁一律以 `serverUpdatedAt`（服务端时间戳）为准，客户端时钟不可信（D-20）。
- 同步触发：App 启动、前台恢复、网络恢复、记录变更后、后台周期任务（双端差异见 2.5）。

### 2.2 幂等与去重

| 项 | 规则 |
|----|------|
| 幂等键 | 客户端为每次上行操作生成 `clientRequestId`（UUIDv4），同一操作的自动重试**复用同一键**，新操作生成新键 |
| 服务端去重 | 服务端维护 `(userId, clientRequestId)` 唯一约束的幂等表；命中重复请求直接返回首次结果（200 + 原响应体），不重复落库 |
| 幂等表保留期 | 7 天〔假设〕；超过后重复请求按普通写入处理（此时 `baseVersion` 校验兜底防错） |
| 跨端幂等 | 同一 `localId` 首次上行成功后服务端返回 `serverId`，客户端建立 `localId ↔ serverId` 映射；后续操作一律携带 `serverId` |

### 2.3 上行（批量）

```
POST /api/v1/sync/push
{
  "ops": [
    {
      "clientRequestId": "uuid",
      "entity": "foodEntry" | "fastingRecord" | "userProfile" | "fastingPlan",
      "op": "create" | "update" | "delete",
      "serverId": "...",            // create 时省略
      "baseVersion": 3,             // update/delete 必带；create 省略
      "payload": { ... },           // 实体字段，UTC 时间戳
      "clientTimestamp": "..."      // 仅审计用途，不参与仲裁
    }
  ]
}
```

- 单批上限 100 条〔假设〕，超出分批串行。
- 响应逐条返回 `ack`（成功 + `serverId`/`serverVersion`/`serverUpdatedAt`）或 `nack`（`code`: 409 / 422 / 其他），客户端按条处理，不因单条失败中断整批。
- 批内顺序：按 `localVersion` 与创建时间升序；同一记录的多个操作合并为最新一个〔假设〕。

### 2.4 下行（增量）

```
GET /api/v1/sync/pull?syncToken=<opaque>&limit=200
→ { "changes": [...], "deletions": [...], "nextSyncToken": "...", "hasMore": false }
```

- `syncToken` 为服务端不透明游标（内部按 `(userId, updatedAt, id)` 游标实现），客户端全量持久化保存；首次同步不传 token → 全量下行。
- 下行数据按实体落入本地库，与本地 `pending`/`submitting` 记录冲突时：本地有未上行修改的记录**不被下行覆盖**，改为按第 3 章合并。
- 服务端 `updatedAt` 一律由数据库时钟赋值（`now()`），禁止接受客户端时间戳作为 `updatedAt`（防腐，第 5 章）。
- 全量重建：重装/换机后首次 pull 全量；数据量大时分页拉取并显示进度〔假设：MVP 单用户数据量小，不做断点续传〕。

### 2.5 双端后台同步差异

| 项 | iOS（15+，D-14） | Android（API 26+，D-14） |
|----|------------------|--------------------------|
| 前台触发 | 启动 / `scenePhase` 进入前台 / 网络恢复（NWPathMonitor） | 启动 / `onResume` / 网络恢复（ConnectivityManager callback） |
| 后台周期 | `BGAppRefreshTask`（系统调度，不保证准点） | WorkManager 周期任务（最小间隔 15 分钟，系统约束） |
| 即时性兜底 | 以前台触发 + 变更后即时上行为主；后台任务仅兜底，不依赖其准时 | 同左 |
| 省电策略 | 低电量模式下后台刷新可能被系统禁用 → 依赖前台触发 | 厂商省电白名单不可控 → 不引导加白名单，依赖前台触发〔假设〕 |

### 2.6 派生数据的同步（DailyNutrition / Streak）

- DailyNutrition 由服务端从 FoodEntry 聚合（PRD 第五章），Streak 由服务端按 D-08/D-12 口径统一计算——**双端口径一致性的唯一保障是不让客户端各自算**。
- 客户端离线期间展示「本地预估」聚合值，角标注明「待云端校准」〔假设〕；联网后以下行服务端值为准覆盖。
- 派生数据无四态、无上行，仅随增量下行刷新。

## 3. 字段级冲突合并（D-20：LWW + 冲突队列）

### 3.1 总则

- 冲突检测：上行 `update/delete` 携带 `baseVersion`，服务端比对当前 `serverVersion`；不一致 → 409 + 返回服务端当前版本全文。
- 合并粒度：**字段级 LWW**，以 `serverUpdatedAt`（服务端时间戳）为唯一仲裁时钟（D-20）。客户端持有各字段的本地修改时间 `fieldUpdatedAt`（UTC，仅作合并输入之一）与服务端逐字段比较〔假设：本地需为可 LWW 字段维护字段级修改时间戳，存于本地库 `fieldMeta` JSON 列〕。
- 不可合并情形（D-20 明确）：**一端删除、另一端修改**——保留双份（本机版 + 云端版）入冲突队列，人工提示处理。

### 3.2 逐实体合并规则表

#### FoodEntry（饮食记录）

| 字段 | 可 LWW | 说明 |
|------|--------|------|
| `datetime`（就餐时间） | ✅ | 时间晚者胜 |
| `foodId` / `amount`（份量）/ `note` | ✅ | — |
| `source`（拍照/语音/常吃/手动） | ✅ | 低价值字段，LWW 即可 |
| `nutritionSnapshot`（营养快照） | ⛔ 不仲裁 | 由 `foodId`+`amount` 重新换算生成，不参与合并 |
| 删除 vs 修改 | ⛔ 不可合并 | 保留双份 → 冲突队列人工选择（D-20） |
| 双端各自新建同餐记录 | 不判冲突 | 视为两条独立记录（`clientRequestId` 不同即不同记录），由用户在记录页自行合并/删除（PRD M3 允许重复记录） |

#### FastingRecord（断食记录）

| 字段 | 可 LWW | 说明 |
|------|--------|------|
| `actualStart` / `actualEnd` / `actualDuration` | ✅ | 时间晚者胜 |
| `plannedWindowStart` / `plannedWindowEnd` | ✅ | 跟随 FastingPlan 快照 |
| `achieved`（是否达标） | ⛔ 不仲裁 | 服务端按 D-08 规则从实际时长重算，客户端不仲裁 |
| `statusChangeLog`（状态变更日志） | ⛔ 追加合并 | append-only，按时间戳并集去重合并，非 LWW〔假设〕 |
| 删除 vs 修改 | ⛔ 不可合并 | 保留双份 → 人工提示 |

#### User 资料

| 字段 | 可 LWW | 说明 |
|------|--------|------|
| `height` / `age` / `gender` / `activityLevel` / `goal` | ✅ | 标量资料，LWW |
| `weight`（体重） | ⛔ 追加合并 | 体重按测量日期为键的历史序列，同日期 LWW、不同日期并存〔假设〕 |
| `accessibilityPrefs` / `themePrefs` / 提醒开关 | ✅ | 逐字段 LWW |
| 账号级字段（手机号、登录方式绑定，D-13） | ⛔ 不在同步范围 | 走账号体系专用接口，不经四态队列 |

#### FastingPlan（断食方案）

| 字段 | 可 LWW | 说明 |
|------|--------|------|
| 整实体（`planType` + `eatingWindowStart/End` + `effectiveDate`） | ✅ 实体级 LWW | 窗口字段强耦合（改一半会产生非法窗口），**按实体整体**取时间晚者胜，不做字段级拆分〔假设〕 |
| `effectiveDate` | ⛔ 服务端赋值 | 更换方案次日 0 点（本地时区）生效（D-06），生效日由服务端按用户时区计算后下发，客户端不仲裁 |
| 历史方案版本 | 不判冲突 | 每次更换生成新 `planId` 的不可变版本，旧版本保留供历史数据回放；「当前方案」指针 LWW |

### 3.3 冲突队列

- 本地维护冲突队列表：`conflictId, entity, localSnapshot(JSON), serverSnapshot(JSON), reasonCode, createdAt`。
- `reasonCode` 枚举：`DELETE_VS_EDIT`（删改冲突）、`NON_MERGEABLE_FIELD`（不可合并字段）、`VERSION_MISMATCH_UNRESOLVED`（自动合并失败兜底）。
- 队列条目不随增量下行自动清除，仅随用户处理动作清除（T12/T13/T14）。
- 同一记录再次冲突：更新队列内既有条目（不堆叠），`createdAt` 刷新〔假设〕。

## 4. UI 规范

### 4.1 「待同步 N 条」可见入口（D-20 强制）

| 位置 | 形态 | 规则 |
|------|------|------|
| 记录页 | 顶部信息条（云白底卡，置于三入口之上） | `pending + submitting + conflicted > 0` 时展示「待同步 N 条」；全部为 0 时隐藏。点击进「同步详情页」 |
| 我的页 | 「数据与同步」设置项，右侧角标显示 N | 常显该设置项；N=0 时显示「全部已同步 ✓」 |
| 同步详情页 | 按状态分组列表（待同步 / 冲突 / 已同步-最近 20 条〔假设〕） | 每条显示实体类型、摘要（如「午餐 · 米饭 150g」）、本地修改时间、「立即重试」按钮 |
| 冲突提示 | 「待同步」入口与我的页角标叠加红点 | 有 `conflicted` 条目时红点常显直至清空；进入 App 且存在冲突时弹一次半屏引导（每次冷启动最多一次〔假设〕） |

文案（对齐品牌语气「简单而非术语」，中英双语走 i18n key，D-15）：
- 待同步：「还有 N 条记录在路上，联网后自动同步」
- 冲突：「这条记录在两台设备上改动不同，请你来定」
- 失败提示：「这条记录没被保存，点这里重新提交」（对应 T7 回滚场景）

### 4.2 同步失败重试策略

| 项 | 规则 |
|----|------|
| 触发方式 | 自动重试（退避）+ 用户手动「立即重试」（立即重置退避计时） |
| 退避算法 | 指数退避：`delay = min(5s × 2^retryCount, 15min)`，加 ±20% 随机抖动 |
| 自动重试上限 | 连续 8 次失败后暂停自动重试，保持 `pending`，仅接受手动重试或下次网络恢复事件唤醒〔假设〕 |
| 重试白名单 | 网络错误、5xx、429 才自动重试；4xx（除 409）不重试（走 T7 回滚） |
| 全局限流 | 429 响应携带 `Retry-After` 时以其为准〔假设〕 |

### 4.3 冲突条目处理界面要求

- 入口：同步详情页冲突分组 → 点击进入冲突处理页。
- 布局：本机版与云端版**并排卡片**展示（字段级 diff 高亮差异字段），字段名用业务文案而非技术字段名（如「就餐时间」而非 `datetime`）。
- 三个操作（按 3.1 可用性过滤）：「保留本机」「保留云端」「合并可合并字段」（逐项选择器）。
- 删除 vs 修改冲突：明示「另一端已删除这条记录」，选项为「恢复并保留修改」/「确认删除」。
- 无障碍（M8 硬性）：三重编码、对比度 ≥4.5:1、读屏标签完整；冲突操作需二次确认（防误触丢数据）。
- 无网络时冲突页可查看双份但「保留本机」操作排队至联网执行，按钮置 loading 说明〔假设〕。

## 5. 防腐层（服务端）

| 层 | 规则 |
|----|------|
| DTO 校验 | NestJS `class-validator` 全量校验（D-17 技术栈）：类型、枚举值、必填、长度、数值范围（如 `amount > 0`、热量非负）、UTC 时间格式 |
| 业务校验 | 拒绝未来超过 24 小时的 `datetime`〔假设〕；`FastingRecord.actualDuration ≤ 48h`〔假设〕；`foodId` 必须存在于食物库（D-16） |
| 时钟防腐 | `serverUpdatedAt`/`effectiveDate` 等一律服务端赋值，客户端传入的同类字段忽略并记审计日志 |
| 脏数据处理 | 校验失败 → 422 + 逐字段错误码；**不入库、不进重试**；客户端按 T7 回滚并封存死信 |
| 告警 | 422 率、`DELETE_VS_EDIT` 冲突率、幂等表命中率接入监控告警〔具体平台待外部确认〕；同一 `clientRequestId` 出现 >2 次重复提交记异常埋点（指示客户端重试逻辑 bug） |
| 限流 | 按 `userId` 限流（同步接口），防单设备刷库〔阈值待外部确认〕 |

## 6. 双端离线场景测试要点

| # | 场景 | 步骤 | 预期 |
|---|------|------|------|
| E1 | 飞行模式记录 → 联网合并 | 飞行模式下新增 3 条 FoodEntry + 改 1 条 → 关飞行模式 | 3 条新增 + 1 条修改全部上行成功转 `synced`；期间「待同步 4 条」入口可见；无重复记录（幂等验证） |
| E2 | 双端同时改同一记录（可合并字段） | iOS 端改 FoodEntry `amount`，Android 端改同一条 `note`，两端先后上行 | 字段级 LWW 合并：两端最终均持有两个新值，`synced`，不进冲突队列 |
| E3 | 双端删改冲突（不可合并） | iOS 端删除记录，Android 端离线修改后联网上行 | 后进一方收到 409 → 转 `conflicted` 进冲突队列，双份保留，UI 红点提示，人工处理后一致 |
| E4 | 撤销与同步竞态 | 确认记录后第 3 秒（撤销窗内）断网 → 第 8 秒点撤销 → 联网 | 请求未发出（T1 〔假设〕行为）→ 本地删除即可，云端无此记录；若实现允许窗内提前上行，则撤销须产生 tombstone 上行并最终云端无记录，两种实现路径都须通过本用例 |
| E5 | 上行在途杀进程 | 提交记录后上行请求发出瞬间强杀 App → 重启 | 重启后该条为 `submitting`/`pending` 可恢复重试；服务端若已收到则幂等命中不重复入账 |
| E6 | 重登一致性 | 存在 5 条 `pending` 时退出登录 → 重新登录同账号 | 5 条 `pending` 原样保留并继续同步（T16）；异账号登录触发 T17 弹窗 |
| E7 | 换机全量恢复 | 新设备登录 → 全量 pull | 全部 `synced` 数据恢复；旧设备 `conflicted` 未处理条目在新设备也可见（冲突队列需随同步下行〔假设〕） |
| E8 | 时钟回拨 | 记录后手动回拨系统时间 1 天 → 再记录并同步 | 数据正常入库；LWW 仲裁不受客户端时钟影响（全部以 `serverUpdatedAt` 为准，D-07/D-20） |
| E9 | 退避与上限 | 服务端持续返回 500 → 观察重试间隔 | 间隔符合 5s→10s→…→15min 封顶曲线（±20% 抖动），8 次后停止自动重试，`pending` 保留 |
| E10 | 防腐拒绝 | 构造非法 payload（负份量/未来 3 天的 datetime）上行 | 服务端 422；客户端按 T7 回滚并提示，不进入无限重试 |
| E11 | 弱网批量 | 2G/丢包 30% 网络下累积 50 条 `pending` → 恢复 | 分批上行（≤100/批）全部成功，期间 UI 不卡死、N 实时递减 |
| E12 | iOS/Android 后台同步 | 记录后立刻切后台，iOS 等待 BGAppRefresh / Android 等待 WorkManager 窗口 | 两端最终均同步成功；不以后台任务为唯一路径（前台恢复必触发补偿同步） |

> E4 的两条实现路径需在 M0 技术方案评审时二选一并固化（撤销窗内是否允许提前上行），当前默认按 T1 〔假设〕：窗内不发请求。

## 7. 数据安全

### 7.1 传输安全

| 项 | 规则 |
|----|------|
| 协议 | 全链路 HTTPS，TLS ≥ 1.2（优先 1.3）〔假设〕；禁用明文 HTTP |
| 证书校验 | 系统证书链校验；证书固定（pinning）〔待外部确认：MVP 是否启用，启用需配套证书轮换预案〕 |
| 认证 | 登录后签发 access token（短期）+ refresh token；同步接口 401 → 刷新后重放原请求（复用同一 `clientRequestId`，幂等保证重放安全） |
| 双端差异 | iOS 开启 ATS 默认合规；Android `networkSecurityConfig` 禁止 cleartextTraffic |

### 7.2 本地库加密

健康数据属敏感个人信息（D-18），本地 SQLite 全库加密：

| 项 | iOS | Android |
|----|-----|---------|
| 加密方案 | SQLCipher（drift 经 `sqlcipher_flutter_libs` 集成）〔假设：选型 sqlcipher_flutter_libs，最终依赖版本 M0 定〕 | 同左 |
| 密钥存储 | iOS Keychain，访问级别 `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`（后台同步需解锁后可读，且不随备份迁移）〔假设〕 | Android Keystore 生成/保管 AES 主密钥，SQLCipher 密钥经其包裹后存私有目录；API 26+ 满足 Keystore 硬件/TEE 能力（D-14） |
| 密钥生命周期 | 首次启动生成 32 字节随机密钥；退出登录不删；卸载即随 Keychain/Keystore 项与库文件一并清除 | 同左 |
| 生物识别绑定 | 不强制绑定（避免影响后台同步读取数据库）〔待外部确认：合规侧是否要求应用锁级别保护〕 | 同左 |
| 降级 | 加密库初始化失败时禁止回退为明文库存储，应阻断并提示重装〔假设〕 | 同左 |

### 7.3 其他

- 日志与埋点中禁止输出记录明文内容（食物名、体重等），仅输出实体类型与 ID（D-18 最小化）。
- 导出/删除（D-18 设置内入口）：导出包含本地未同步数据并给出提示；账号删除走 1.5 服务端清除流程。
- 备份排除：iOS 将本地库目录标记 `isExcludedFromBackup`（云端已有同步，避免加密库明文备份语义混乱）〔假设〕；Android 配置 `android:allowBackup` 排除该目录〔假设〕。
