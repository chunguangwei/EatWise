## 一、埋点技术约定

### 1.1 事件命名规范

| 规则 | 说明 | 正例 | 反例 |
|------|------|------|------|
| 全部小写 snake_case | 事件名与属性名统一小写字母 + 数字 + `_`，禁止驼峰/连字符 | `fasting_end_confirm` | `FastingEndConfirm`、`fasting-end` |
| 结构 `模块_对象_动作` | 模块前缀见下表；对象可省略；动作用动词过去/现在式 | `record_entry_camera_click` | `click_camera` |
| 一对事件用 `_start` / `_end`（或语义化后缀） | 耗时类事件必须成对，见 2.5 | `record_flow_start` / `record_flow_success` | 只埋一个事件无法算耗时 |
| 曝光后缀 `_expose`、点击后缀 `_click`、提交后缀 `_submit`、结果后缀 `_success`/`_fail` | 五类后缀固定，便于 SQL 聚合 | `plan_recommend_expose` | `plan_show` |
| 版本演进不改名 | 已上线事件名永不变更；语义变化新增事件，旧事件标记 `deprecated` | — | 改已上线事件名导致历史断裂 |
| 语言 | 事件名与属性名一律英文；属性值枚举用英文小写枚举，禁止中文值 | `entry_type: "camera"` | `entry_type: "拍照"` |

**模块前缀表**（与 PRD 模块对应）：

| 前缀 | 模块 | 前缀 | 模块 |
|------|------|------|------|
| `onboard_` | M1 新手引导与方案库 | `analytics_` | M4 营养可视化分析 |
| `fasting_` | M2 断食计时与提醒 | `community_` | M5 社区与激励 |
| `record_` | M3 快捷饮食记录 | `account_` / `sync_` / `privacy_` / `settings_` | M7 账号、数据与设置 |
| `app_` / `push_` / `widget_` | 全局（启动、通知、小组件） | `page_` / `element_` | 通用页面停留与曝光（见第四章） |

### 1.2 公共属性（Common Properties）

所有事件自动附带以下公共属性，由客户端 SDK 层统一注入，业务代码不得手工拼写。

| 属性名 | 类型 | 示例 | 说明与规则 |
|--------|------|------|------------|
| `event_id` | string (UUIDv4) | `"3f8a…e21"` | 客户端生成，服务端按 `event_id` 幂等去重（防重试重复上报） |
| `event_name` | string | `"record_flow_success"` | 见 1.1 |
| `timestamp` | int64 | `1753600000000` | **UTC 毫秒时间戳**（事件发生的本地时刻转 UTC，与 D-07 全链路 UTC 存储一致）；本地时区换算在分析层完成 |
| `client_date` | string | `"2026-07-27"` | 事件发生时的设备本地自然日（yyyy-MM-dd），用于按「本地日」口径计算留存/有效记录日，避免 UTC 日界误切 |
| `user_id` | string | `"u_9f2c…"` | 登录后为服务端下发的用户 ID；**上报与分析环节使用哈希化匿名 ID**〔假设：`HMAC-SHA256(user_id, salt)`，salt 仅数据平台持有，明细层不落明文手机号/账号〕 |
| `anonymous_id` | string | `"a_4d1e…"` | 未登录（授权前不采集，见 1.6；授权后未登录阶段）使用的设备级匿名 ID，登录后与 `user_id` 做 ID-Mapping 合并 |
| `device_id` | string | `"d_7b33…"` | 首次启动生成的随机 UUID，持久化于 Keychain(iOS)/Keystore+SharedPreferences(Android)；**iOS 不采集 IDFA**〔假设〕，Android 不采集 IMEI/OAID 之外的可重置 ID 之外字段，OAID 仅国内合规需要时采集〔待外部确认：法务，D-18〕 |
| `platform` | string enum | `"ios"` / `"android"` | 二值 |
| `os_version` | string | `"17.5.1"` / `"14"` | 系统版本 |
| `app_version` | string | `"1.0.0"` | 语义化版本 |
| `build_number` | string | `"102"` | 构建号，灰度对比用 |
| `locale` | string enum | `"zh-CN"` / `"en"` | 当前 App 语言（D-15：中英双语，跟随系统/手动切换），注意与系统语言区分 |
| `system_locale` | string | `"zh-Hans-CN"` | 系统语言，用于评估语言跟随策略 |
| `network` | string enum | `"wifi"` / `"cellular"` / `"offline"` / `"none"` | 事件发生时的网络类型；`offline` 事件进入本地缓存（见 1.5） |
| `screen_width` / `screen_height` | int | `393` / `852` | 逻辑像素，适配分析用 |
| `session_id` | string | `"s_20260727_…"` | 会话 ID：App 进入前台生成，退到后台 >30 秒再回前台视为新会话〔假设：30 秒阈值，主流分析平台默认口径〕 |
| `is_first_open_day` | bool | `true` | 是否安装后首个自然日，用于新用户指标快速过滤 |

### 1.3 SDK 选型与上报架构

**选型结论**：自建上报通道（客户端 → 后端 NestJS 采集网关 → 数据仓库）为主通道；第三方分析平台（神策 或 Firebase Analytics）二选一作辅助看板，**最终选型 M0 拍板**〔待外部确认：M0 技术选型会〕。

| 项 | 自建通道（必选） | 第三方平台（M0 二选一） |
|----|------------------|--------------------------|
| 用途 | 指标口径的唯一权威来源（北极星、留存、耗时） | 产品/运营自助看板与漏斗 |
| 理由 | 健康数据属敏感个人信息（D-18），核心明细数据不出自有后端；口径需可 SQL 复算 | 降低看板开发成本 |
| 事件覆盖 | 本字典 100% 事件 | 核心事件子集（白名单，不含任何健康明细属性，如食物名、体重值） |
| 候选 | — | 神策（国内合规与私有化能力强）/ Firebase Analytics（海外扩展好，国内可用性受限） |

**客户端实现（Flutter）**：封装 `AnalyticsService` 单例（Riverpod provider），内部双通道 fan-out；第三方 SDK 仅在隐私授权后初始化与启动（见 1.6），未授权时 `AnalyticsService` 仅写本地加密缓存不上报〔假设：授权前不缓存、直接丢弃，从严执行 D-18 最小化收集〕。

### 1.4 客户端事件模型

```json
{
  "event_id": "3f8a…e21",
  "event_name": "record_flow_success",
  "timestamp": 1753600000000,
  "client_date": "2026-07-27",
  "common": { "user_id": "u_…", "platform": "ios", "app_version": "1.0.0", "locale": "zh-CN", "network": "wifi", "session_id": "s_…" },
  "properties": { "entry_type": "camera", "duration_ms": 12400 }
}
```

- 事件体 = 公共属性（`common`）+ 事件私有属性（`properties`），私有属性以第三章字典为准，**禁止上报字典外属性**（防夹带 PII）。
- 属性类型只允许 `string / int / double / bool / string[]`；枚举值在字典中列全，新增枚举值须走字典评审。
- 时间相关属性一律 UTC 毫秒；「归属自然日」类口径一律用 `client_date` 或由服务端按用户时区重算，与 D-07 一致。

### 1.5 批量上报与离线缓存

| 规则 | 约定值 | 说明 |
|------|--------|------|
| 本地队列 | SQLite（drift，与 D-17 本地存储栈一致）加密表 | 事件先入队再上报，进程被杀不丢 |
| 批量触发 | ≥20 条 或 距上次上报 ≥30 秒，先到先发〔假设〕 | Wi-Fi 下阈值可放大一倍 |
| 立即上报事件（flush now） | `record_flow_success`、`fasting_checkin_success`、`onboard_plan_start`、`privacy_consent_change` | 关键转化事件不等批量，降低丢失率 |
| 网络类型策略 | `cellular` 下正常批量；`offline` 只入队 | 断网不产生流量与重试风暴 |
| 重试 | 指数退避（1s/2s/4s…上限 5 分钟），HTTP 2xx 视为成功；4xx 丢弃该批并记 `app_track_error`；5xx 重试 | 服务端按 `event_id` 幂等，重试不产生重复 |
| 缓存上限 | 最多保留 7 天 / 10 万条，超出按 FIFO 丢弃并记 `app_track_drop`〔假设〕 | 与 D-20 离线可用目标对齐 |
| 时序 | 批量包内按 `timestamp` 升序；服务端以 `timestamp` 为准排序，不以到达顺序为准 | 离线回补事件不扭曲漏斗 |

**双端差异**：iOS 后台执行受系统限制，进入后台时在 `applicationDidEnterBackground` 触发一次 flush（后台任务时限内尽力完成）；Android 用 WorkManager 注册周期兜底任务（≥15 分钟），Doze 模式下由 WorkManager 延迟执行。两端前台行为一致。

### 1.6 隐私合规红线（对齐 D-18）

| # | 规则 | 实现 |
|---|------|------|
| 1 | **未授权前不采集**：首次启动隐私弹窗（D-18）获得同意前，SDK 不初始化、事件丢弃、不生成/不上传 `device_id` | 启动门控：`AnalyticsService` 初始为 disabled，同意后才启用 |
| 2 | **可关闭**：设置内提供「数据分析开关」（与隐私授权分开），关闭后停止一切采集与第三方 SDK 上报，已缓存队列清空 | 开关变更上报 `privacy_consent_change`（该事件本身经自建通道上报一次后即停采） |
| 3 | **最小化**：字典外属性禁止上报；健康明细（食物名、体重数值、断食时长数值）只进自建通道，不进第三方平台 | 白名单由数据侧维护，CI 校验 |
| 4 | **匿名化**：分析层不落地手机号/微信号等直接标识；`user_id` 哈希化（见 1.2） | ETL 层完成，明细库与分析库分离 |
| 5 | **可删除**：用户注销/删除数据时，事件明细按 `user_id` 同步删除（含离线未上报队列） | 与 D-18 导出/删除入口共用链路 |
| 6 | **系统权限声明**：iOS ATT：MVP 不做广告归因，**不请求 ATT**〔假设〕；Android 13+ 通知权限与埋点无关，不因埋点索取任何权限 | 上架材料与 SDK 权限清单公示（D-18） |
| 7 | **儿童与未成年人**：不单独采集可识别未成年用户的分析标签〔待外部确认：法务〕 | — |

## 二、核心指标口径实现

> 目标值以 PRD 1.4 + D-01 为准：引导完成率 ≥70%、次日记录留存 ≥45%、7 日断食打卡留存 ≥30%、单次记录中位耗时 ≤15 秒、D21 留存 ≥18%。
> 所有指标的**日界一律按用户本地自然日**（`client_date`，与 D-07 归属日规则一致）。

### 2.1 北极星：WAU-Active（D-01）

- **定义**：自然周（周一 00:00 起，本地时区）内累计 ≥4 个「有效记录日」的去重用户数。
- **有效记录日**（D-01）：当日断食打卡达标（D-08）**或** 当日有 ≥1 条饮食记录。

| 依赖事件 | 判定逻辑 |
|----------|----------|
| `fasting_checkin_success` | `is_qualified=true`（D-08 达标）且 `client_date = 归属日`（归属日 = 进食窗口所属自然日，D-07）→ 该日为有效记录日 |
| `record_flow_success` | 该事件发生的 `client_date` → 该日为有效记录日（撤销不回扣：撤销事件 `record_undo_click` 若使当日记录归零，则该日不计，按最终态判定） |

- **计算口径**：`count(distinct user_id) where 周内有效记录日数 >= 4`；按周分区表日更。
- **排除**：测试账号白名单（`is_internal=true`，数据侧维护）；卸载重装用户按 `user_id` 去重不受影响。

### 2.2 引导完成率

- **定义**：新用户中「完成 3 题问卷并启动方案」的占比。分母 = 当日新增用户（首次 `app_open` 且 `is_first_open_day=true` 且完成注册）；分子 = 其中触发 `onboard_plan_start` 的用户。
- **漏斗**（依赖事件）：`onboard_guide_expose` → `onboard_question_answer`(q=1,2,3) → `onboard_plan_recommend_expose` → `onboard_plan_start`；`onboard_skip_click` 走兜底分支（D-03），**不计入分子**，单列「跳过率」监控。
- **口径备注**：分子允许在注册后 7 日内回补完成〔假设〕，报表同时给出「当日完成率」与「7 日回补完成率」两个口径。

### 2.3 次日记录留存

- **定义**：注册日（D0）后第 1 个本地自然日（D1）仍有「记录行为」的用户占比。「记录行为」= 有效记录日判定（同 2.1，取 `record_flow_success` 或达标 `fasting_checkin_success`）。
- **口径**：`D1 有记录行为的新用户数 / D0 新增用户数`，按 D0 队列（cohort）追踪。
- **依赖事件**：`app_open`（判定活跃窗口）、`record_flow_success`、`fasting_checkin_success`。

### 2.4 7 日断食打卡留存

- **定义**：D0 注册队列中，D6 之前（含 D6，7 日内）最后一天仍在使用断食计时的用户占比〔假设：以「D1–D7 任意一天产生 ≥1 次 `fasting_checkin_success`（含不达标，即真实完成一次断食流程）」判定「仍在使用」，避免与达标率混淆〕。
- **同时输出**辅助口径：7 日内 ≥1 天「达标」的占比（供观察 D-08 容差影响）。
- **依赖事件**：`fasting_checkin_success`（含 `is_qualified` 属性）、`fasting_state_change`。

### 2.5 单次记录耗时（≤15 秒验收口径）

- **事件对**：起点 `record_flow_start`（进入记录页/启动任一入口时触发，含 `flow_id`）→ 终点 `record_flow_success`（确认记录且乐观更新入账成功，同 `flow_id`，含 `duration_ms`）。
- **计时规则**：
  - `duration_ms` 由客户端打点：`record_flow_success.timestamp − record_flow_start.timestamp`；客户端时钟不可信时以服务端收到的事件对差值复核〔假设：以客户端打点为主口径，服务端复核偏差 >10% 的样本剔除〕。
  - 中途退到后台再回来：若暂停累计 >30 秒，该样本剔除（记 `record_flow_abandon`，`reason=background_timeout`）。
  - 撤销（`record_undo_click`）不影响耗时样本；识别失败转手动兜底的样本**计入**（真实用户路径，符合 PRD「兜底不阻断」）。
- **统计方式**：**中位数（P50）为主验收口径**，同时看 P90；按 `entry_type`（camera/voice/frequent/manual）分维度。验收标准：主流程 P50 ≤ 15 秒（PRD US-3.1）。
- **「≤3 步」口径**：`record_flow_success.step_count`（用户有效交互步数，不含曝光）≤ 3 为达标，报表给达标率。

### 2.6 D21 留存

- **定义**：D0 注册队列中，第 21 个本地自然日（D21）仍活跃的用户占比。「活跃」= 当日有任一核心业务事件：`app_open` 且产生 ≥1 个有效记录日判定事件，或 `fasting_checkin_success` / `record_flow_success` / `community_post_publish` 任一发生〔假设：采用「核心行为活跃」而非纯打开，避免通知误点虚高；纯 `app_open` 口径作为对照报表并行输出〕。
- **依赖事件**：`app_open`、`record_flow_success`、`fasting_checkin_success`、`community_post_publish`。

### 2.7 指标—事件依赖总表

| 指标 | 目标 | 关键依赖事件 | 主口径 |
|------|------|--------------|--------|
| WAU-Active | — | `fasting_checkin_success`、`record_flow_success` | 周 ≥4 有效记录日（2.1） |
| 引导完成率 | ≥70% | `onboard_*` 全链 | 2.2 |
| 次日记录留存 | ≥45% | `record_flow_success`、`fasting_checkin_success` | 2.3 |
| 7 日断食打卡留存 | ≥30% | `fasting_checkin_success` | 2.4 |
| 单次记录耗时 | P50 ≤15s | `record_flow_start` / `record_flow_success` | 2.5 |
| D21 留存 | ≥18% | `app_open` + 核心行为事件 | 2.6 |

## 三、全量事件字典

> 属性表「类型」列：`s`=string、`i`=int、`f`=double、`b`=bool、`e`=string enum。所有事件自动携带 1.2 公共属性，下表只列私有属性。
> 「对应指标」列引用第二章编号或业务监控项。

### 3.0 全局事件（app_ / push_ / widget_）

#### `app_open` — App 启动/回前台

- **触发时机**：冷启动完成首帧，或后台回前台且构成新 session（见 1.2 `session_id`）。

| 属性 | 类型 | 示例 | 说明 |
|------|------|------|------|
| `launch_type` | e | `"cold"` / `"warm"` | 冷/热启动 |
| `source` | e | `"icon"` / `"push"` / `"widget"` / `"deep_link"` | 启动来源；push 时附 `push_id` |
| `push_id` | s | `"p_8821"` | 可空，仅 `source=push` |

- **对应指标**：2.3 / 2.6（活跃判定）、各留存分母。

#### `app_track_error` / `app_track_drop` — 埋点通道自监控

- **触发时机**：批量上报收到 4xx 丢弃 / 本地队列超上限丢弃。

| 属性 | 类型 | 示例 |
|------|------|------|
| `error_code` | i | `413` |
| `dropped_count` | i | `42` |

- **对应指标**：数据质量监控（丢事件率 <0.1% 告警〔假设〕）。

#### `scroll_depth` — 滚动深度（页面/组件级）

- **触发时机**：页面主体滚动区滚动到 25 / 50 / 75 / 100 档位时各触发一次（口径同 4.2：按**最大**滚动深度，回滚不回落；内容不足一屏、无法滚动等同 100）。

| 属性 | 类型 | 示例 | 说明 |
|------|------|------|------|
| `page` | e | `"home"` / `"analytics"` / `"analytics_reports"` / `"record"` | 字典 `page_id`（附录 B），与 `page_stay.page_id` 同源 |

- **与 4.2 的关系**：`page_stay.scroll_depth`（页面停留内联的最大深度）为规范原口径；客户端实现改由本事件独立上报（档位化、可做漏斗分档），`page_stay` 不再内联该属性。

## 四、曝光类事件去重与页面停留规范

### 4.1 曝光事件规则

| 规则 | 约定 | 适用事件 |
|------|------|----------|
| 可视判定 | 元素 ≥50% 面积进入视口且停留 ≥500ms 才计曝光〔假设：主流口径〕 | 所有 `_expose` |
| 会话内去重 | 同一 `session_id` 内同一页面/元素的同一曝光事件只上报一次（以 `event_name + page_id + element_key` 为去重键）；Tab 切走再切回**不重复计** | `_expose` 全部 |
| 跨会话重新计 | 新 `session_id`（见 1.2 定义）允许再次曝光 | `_expose` 全部 |
| 内容变化重计 | 同元素内容实体变化（如 `attribute_date` 变化、`signal_level` 变化、推荐结果重算）计为新曝光，需将内容键（如 `nutrient+signal_level`）纳入去重键 | `signal_card_expose`、`fasting_ring_expose` |
| 列表类曝光 | 打卡流等列表按卡片逐条计，去重键含 `post_id_hash`；快速滑动（单卡片可视 <500ms）不计 | `community_*` 曝光 |
| 曝光只在客户端判定 | 服务端不补曝光；页面数据请求 ≠ 曝光 | — |

### 4.2 页面停留时长规范

- **页面级停留**：每个一级/二级页维护 `page_view_start` / `page_view_end` 内部计时（不单设事件名，作为 `page_stay` 事件上报）：

| 属性 | 类型 | 说明 |
|------|------|------|
| `page_id` | e | `home` / `record` / `analytics` / `community` / `profile` / 二级页见附录 B |
| `stay_ms` | i | 停留毫秒 |
| `scroll_depth` | i | 最大滚动深度百分比 0–100（客户端实现已收口为独立事件 `scroll_depth`，见 3.0；`page_stay` 不再内联本属性） |
| `end_reason` | e | `"tab_switch"` / `"navigate"` / `"background"` / `"exit"` |

- **计时规则**：退到后台即暂停计时（`end_reason=background` 结算一段），回前台构成同 session 时新开一段；页面停留报表按 `page_id` 聚合 P50/P90。
- **与 2.5 的关系**：记录页 `stay_ms` 不等于「单次记录耗时」——后者以 `record_flow_start/success` 事件对为准（2.5），`page_stay` 仅作体验参考。
- **双端差异**：iOS 的 Tab 切换不产生页面销毁，Android 在低内存下页面可能被回收重建——停留计时以路由层 `didPush/didPop`（Flutter RouteObserver）为准，与原生生命周期解耦，两端行为一致。

### 5.1 三级验收流程

| 阶段 | 责任人 | 动作 | 产出 / 通过标准 |
|------|--------|------|------------------|
| ① 开发自测 | 客户端开发 | 按本字典实现后，用内置 Debug 埋点面板（实时事件流 + 属性 JSON 视图）逐事件触发；断网/弱网/杀进程场景验证 1.5 缓存与重试；iOS、Android 真机各过一遍 | 自测录屏 + 事件流截图附 PR；命名/类型/枚举与字典 100% 一致（CI lint 校验，见 5.3） |
| ② 数据侧校验 | 数据工程师 | 灰度环境数据回放：核对事件到达率（客户端发送数 vs 入库数）、字段解析成功率、`event_id` 去重率、核心漏斗（引导/记录）可复算；对照第二章口径跑通全部 6 个核心指标的 SQL | 校验报告：到达率 ≥99.9%、解析失败率 <0.1%、6 个核心指标 SQL 全部出数 |

### 5.2 上线前事件覆盖 Checklist

- [ ] 第三章字典中属于本版本范围（MVP：全局 + M1 + M2 + M3 + M7；V1.1：+ M4 + M5 基础）的事件 **100% 实现**，无遗漏、无字典外事件。
- [ ] 每个事件触发时机与字典一致，抽查路径覆盖：正常流程、异常流程（识别失败/离线/权限拒绝）、边界（跨午夜断食、D-08 容差、D-11 10 秒撤销窗）。
- [ ] 事件对完整性：随机抽 50 个 `flow_id`，`record_flow_start` 与 `record_flow_success/abandon` 配对率 = 100%。
- [ ] 核心指标 6 项（2.1–2.6）在灰度数据上可复算，且与看板数值一致。
- [ ] 隐私合规 7 条（1.6）逐条真机验证通过，含未授权抓包验证零上报。
- [ ] 双端一致性：同一操作路径在 iOS / Android 产生的事件名、属性、枚举值完全一致（公共属性中 `platform`/`os_version` 除外）。
- [ ] 离线缓存：飞行模式下产生事件 → 联网后 5 分钟内全部入库且无重复。
- [ ] 曝光去重：同 session Tab 往返 3 次，`_expose` 事件仅 1 条。
- [ ] 性能：批量上报在主线程无阻塞；冷启动因埋点初始化增加的耗时 <50ms〔假设〕。

### 5.3 工程保障

- **字典即代码**：事件 Schema（名称/属性/类型/枚举）维护为机器可读的 `tracking_schema.yaml`〔假设：存放于客户端仓库 `analytics/` 目录〕，CI 对埋点代码做静态 lint：字典外事件/属性直接编译失败。
- **变更流程**：新增/修改事件 → 修改本字典与 schema（同 PR）→ 数据侧评审 → 合入。已上线事件只允许追加可选属性，禁止删属性、改类型、改枚举语义（1.1）。
- **Debug 面板**：客户端内置埋点调试浮层（仅 Debug/灰度包），展示实时事件流、队列长度、最近一次上报结果，供 5.1-① 使用。
