# 《明食 · EatWise — 技术选型与双端架构》v1.0

> 本文档是「明食 · EatWise」iOS + Android 双端开发的技术总纲，承接 PRD v1.0、设计方案定稿、需求评审记录，并以《开放问题决策记录》为最高优先级锚点（引用处标注 D-XX）。
> 适用范围：客户端（Flutter）、后端（NestJS）、DevOps 与工程规范全链路。
> 标注约定：`〔假设〕` = 合理推断待团队确认；`〔待外部确认〕` = 需外部方（厂商/法务/营养侧）确认。

## 一、技术选型对比与结论（D-17）

### 1.1 候选方案对比表

| 维度 | Flutter 3.x | React Native (Hermes) | 原生双端（Swift/Kotlin） |
|------|-------------|----------------------|--------------------------|
| **双端一致性** | 自绘渲染引擎，像素级一致；可直接满足设计稿「跨触点一致性 ≥95%」要求（D-17） | 依赖系统组件，双端表现存在差异，需额外调平 | 两套代码，一致性靠人工对齐，成本高 |
| **性能** | AOT 编译 + Skia 渲染，60/120fps；计时环、微交互（设计稿 5.1）实现可靠 | JS 桥接，复杂动画/高频刷新（每秒倒计时）易掉帧 | 最优，但本项目非重度图形/计算场景，优势不显著 |
| **小组件 / Live Activity** | 需原生桥：iOS WidgetKit + Live Activity（iOS 16.1+）/ Android AppWidget，经 `home_widget` + MethodChannel 实现，一次桥接双端复用 | 同样需原生桥，且 JS 与原生混合调试链路更长 | 原生直达，无桥接成本 |
| **本地通知 / 后台能力** | `flutter_local_notifications` 成熟，封装 UNUserNotificationCenter / NotificationChannel | `notifee` 等可用，生态略碎片化 | 原生直达 |
| **团队与招聘** | 单团队维护双端，人力成本约为原生双端的 55%–65%；Dart 上手快，Web/iOS/Android 背景工程师均可转入〔假设〕 | JS/TS 人才池最大，但资深 RN 人才稀缺 | 需 iOS、Android 两个团队，成本最高 |
| **生态成熟度** | Google 官方维护，pub.dev 生态完善；drift/go_router/dio/Riverpod 一线库齐全 | 生态大但质量参差，升级断代风险高 | 生态最成熟，但重复建设 |
| **对本项目关键依赖的适配** | Token/主题体系可直接映射为 `ThemeExtension`（D-17）；drift 支撑本地优先 + 四态持久化（D-20）；slang 支撑中英双语（D-15） | 本地优先与复杂状态机需自研胶水层较多 | 每项能力都要做两遍 |

### 1.2 结论

**采用 Flutter（稳定版 3.x）单代码库出 iOS + Android 双端（D-17 已定）。**

核心理由：
1. 设计稿「跨触点一致性 ≥95%」与三重编码无障碍规范（M8）要求双端像素与交互一致，Flutter 自绘渲染天然满足；
2. 断食计时环、信号灯卡片、乐观更新微交互（<100ms 反馈）属于高频 UI 场景，Flutter 性能余量充足；
3. 单团队双端，匹配 MVP 阶段人力与迭代速度约束；
4. 小组件、Live Activity 等系统能力经原生桥补齐，成本可控且有成熟路径（见第三章）。

**锁定版本与基线**：Flutter 稳定版 3.x（以 M0 启动时最新 stable 为准并锁定 `pubspec.lock`）；Dart 3.x；最低系统版本 **iOS 15+ / Android 8.0（API 26）+**（D-14）。

## 二、客户端架构

### 2.1 分层架构

采用 Clean Architecture 四层，依赖方向只允许 `presentation → application → domain ← infrastructure`（domain 不依赖任何外层）：

| 层 | 职责 | 内容 | 禁止事项 |
|----|------|------|----------|
| **presentation** | UI 与用户交互 | 页面（Screen）、Widget、Riverpod 的 UI 侧 Provider、路由绑定、设计 Token / `ThemeExtension` | 直接调用 dio / drift；写业务规则 |
| **application** | 用例编排 | UseCase / Service（如「结束断食」「确认记录」「信号灯判定」编排）、状态机驱动、四态持久化状态暴露 | 出现 Flutter Widget 依赖；出现 SQL / HTTP 细节 |
| **domain** | 纯业务规则 | 实体（User / FastingPlan / FastingRecord / FoodEntry / DailyNutrition / Streak / Post）、值对象、**纯函数规则引擎**（TDEE 公式 D-04、信号灯阈值 D-05、断食状态机 D-07/D-08、streak 规则 D-12）——全部为无依赖 Dart 代码，全量单测 | 依赖 Flutter SDK、第三方库 |
| **infrastructure** | 外部世界适配 | drift DAO/表、dio API Client、i18n（slang）、本地通知封装、小组件桥（MethodChannel）、Keychain/Keystore、推送 SDK、同步引擎（LWW + 冲突队列 D-20） | 直接暴露给 presentation（必须经 application 的接口） |

关键约束（对应评审「必须解决」项）：
- TDEE 公式与红黄绿阈值（D-04/D-05）在 domain 层实现为**纯函数 + 全量单测 + 公式热配置**（服务端下发配置覆盖默认值，本地缓存兜底），营养侧书面背书前通过配置开关不暴露 M4 入口。
- 断食计时状态机（D-07/D-08/D-10）为 domain 层独立模块，时间戳一律 **UTC 存储**，渲染按设备本地时区换算；归属日 = 进食窗口所属自然日；该模块是 M0 第一周 Spike 的验收对象。
- 同步引擎（D-20）在 infrastructure 层实现：记录四态（`syncing / synced / pending / conflict`）持久化于 drift，字段级 LWW（以服务端时间戳为准）+ 冲突队列，客户端生成 `clientRequestId` 保证幂等。

### 2.2 关键依赖清单（D-17）

| 能力 | 选型 | 说明 |
|------|------|------|
| 状态管理 | **Riverpod**（flutter_riverpod + riverpod_generator） | 编译期安全、可测试；UI 状态与业务状态分离 |
| 本地数据库 | **drift（SQLite）** | 类型安全 SQL；承载本地优先存储与四态持久化（D-20）；迁移用 schema version + migration 策略 |
| 路由 | **go_router** | 声明式路由，5 Tab ShellRoute + 二级页栈；深链支持 |
| 网络层 | **dio** + retrofit〔假设〕 + pretty_dio_logger（仅 dev） | 拦截器统一鉴权（AccessToken 刷新）、错误归一化、`clientRequestId` 注入 |
| 国际化 | **slang**（+ intl） | 中英双语（D-15），类型安全 key，禁止硬编码文案；UI 文案/信号灯建议/通知文案/趣味文案全走 i18n |
| 本地通知 | **flutter_local_notifications** | 窗口提醒（D-09）走本地通知，不依赖推送在线 |
| 小组件 | **home_widget** + 原生 MethodChannel | 见第三章桥接表 |
| 密钥存储 | **flutter_secure_storage**（Keychain / Keystore） | Token、refresh token、加密密钥不落明文 |
| 图片 | cached_network_image + image_picker + 压缩（flutter_image_compress） | 打卡图上传前压缩，懒加载 |
| 崩溃监控 | Sentry Flutter（见 5.4 结论） | release 模式全量接入 |
| 环境配置 | `--dart-define` + envied〔假设〕 | dev/staging/prod 三环境（见第六章） |
| 序列化 | freezed + json_serializable | 不可变模型 |
| Lint | flutter_lints + 项目自定义规则（见 7.3） | CI 强制 |

## 三、双端能力差异与实现桥接表

> 原则：能用 Flutter 插件双端统一的优先插件；系统独占能力（小组件、Live Activity、ASR）走原生桥，桥接口在 Dart 侧收敛为统一抽象，上层不感知平台差异。最低版本 iOS 15 / Android API 26（D-14）。

| 能力 | iOS 实现 | Android 实现 | 桥接方式 / 插件 | 关键差异与降级策略 |
|------|----------|--------------|----------------|--------------------|
| **本地通知**（窗口提醒 D-09） | UNUserNotificationCenter；需申请 `alert/badge/sound` 权限；前台展示需实现 `willPresent` 回调 | NotificationChannel（按「窗口提醒/通用」分渠道，用户可在系统设置单独关闭）；Android 13+ 需申请 `POST_NOTIFICATIONS` 运行时权限；Android 12+ 精确闹钟需 `SCHEDULE_EXACT_ALARM` | `flutter_local_notifications` 统一封装；频道/分类在插件初始化时双端注册 | 权限被拒 → App 内顶部横幅引导（D-09），计时不受影响；iOS 勿扰/专注模式与 Android DND 均尊重系统设置 |
| **锁屏/桌面小组件**（M2 倒计时同步） | iOS 15：WidgetKit（SwiftUI，Timeline 刷新）；**iOS 16.1+：Live Activity（ActivityKit）** 锁屏实时倒计时 | AppWidget（RemoteViews / Glance）+ WorkManager 周期刷新；锁屏页无小组件，用常驻通知样式替代〔假设〕 | `home_widget` 负责数据共享（App Group / SharedPreferences 写 UTC 时间戳与状态）；复杂交互经原生 **MethodChannel** 由原生侧直接读共享数据自渲染 | **iOS 15.0–16.0 降级为普通 WidgetKit Widget**（D-14 已定）；小组件倒计时与 App 内误差 ≤1 分钟：共享数据写「状态 + 目标 UTC 时间戳」，原生侧本地算倒计时，不做秒级推送刷新；Timeline 刷新粒度 1 分钟对齐 |
| **系统 ASR**（M3 语音录入 D-16） | Speech framework（SFSpeechRecognizer），需 `NSSpeechRecognitionUsageDescription` + 麦克风权限 | SpeechRecognizer API（`RECORD_AUDIO` 权限）；无 GMS 的国内机型需降级策略 | 自研 MethodChannel 封装统一 `start/stop/partialResult` 接口〔假设：pub 无维护良好的双端统一插件〕 | 解析侧双端统一：识别文本 → 食物库词典匹配 + 份量正则（D-16，不引入 NLP 服务）；国内无 GMS 机型 SpeechRecognizer 不可用时 → 降级提示「当前设备不支持语音录入」，手动搜索/常吃复用兜底 |
| **推送**（营销/社区互动；窗口提醒不依赖推送） | APNs（token 经服务端注册） | 海外：FCM；**国内：厂商通道（华为/小米/OPPO/vivo/荣耀）经聚合推送 SDK** | 客户端用统一 Push 抽象层：token 上报、点击路由（go_router 深链）、静默数据处理 | 聚合 SDK 选型**个推或极光，M0 定〔待外部确认：商务与合规评估〕**；FCM 仅随海外上架（D-15 上架区域）启用；SDK 清单与权限需公示（D-18） |
| **应用内密钥存储** | Keychain（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`，防备份外泄） | Android Keystore 加密 + EncryptedSharedPreferences | `flutter_secure_storage` 统一封装 | 存储对象：access/refresh token、本地库加密密钥；卸载重装视为新设备重新登录；截图/日志严禁输出 |
| **数据共享（App ↔ 小组件）** | App Groups（`group.com.eatwise.shared`）〔假设 bundle 前缀〕 | SharedPreferences（MODE_PRIVATE） | `home_widget` | 共享内容仅限渲染必需的最小数据集（状态、目标时间戳、今日信号灯摘要），健康明细不进共享存储（D-18 最小化） |
| **后台任务**（同步补偿、小组件刷新） | BGTaskScheduler（BGAppRefreshTask），系统调度不保证时机 | WorkManager（周期 ≥15 分钟，Doze 兼容） | `workmanager` 插件 + iOS 原生回调注册 | 后台同步只是补偿：主路径仍是前台/回前台时触发同步引擎（D-20）；不依赖后台任务保证数据一致性 |

## 四、后端架构（D-17）

### 4.1 技术栈与模块划分

**NestJS（Node.js LTS + TypeScript）+ PostgreSQL + Redis**，REST API（契约详见《技术-后端 API 契约》）。

| 模块 | 职责 | 关键设计 |
|------|------|----------|
| **auth** | 注册/登录/token | 手机号验证码（主）+ 微信登录 + Sign in with Apple（D-13）；JWT access（短）+ refresh（长，Redis 黑名单吊销）；验证码限流防刷 |
| **user** | 资料与偏好 | 基础信息（TDEE 输入）、主题/无障碍/语言偏好、隐私授权记录（D-18 单独同意）、数据导出/删除入口 |
| **fasting** | 方案与断食记录 | 方案 CRUD（次日生效 D-06）、断食记录、达标判定复核（D-08 容差 15 分钟走服务端配置热调）、归属日计算（UTC 存储，D-07） |
| **food** | 食物库 | 自建核心库 ≥3000 条（中国食物成分表 + USDA FDC 清洗合并，D-16），中英双语条目与别名（D-15）；版本化下发客户端缓存 |
| **nutrition** | 目标与信号灯 | TDEE/阈值规则以**热配置**形式下发（D-04/D-05，背书前默认值不对外启用 M4）；DailyNutrition 聚合 |
| **social** | 打卡/streak/互动 | 打卡发布（**先审后发**，接阿里云或腾讯云内容安全 API，M0 定〔待外部确认〕，异常转人工队列）、streak 与补签卡（D-12，服务端权威）、点赞 |
| **sync** | 数据同步 | 增量同步（`updatedAt` 游标）、`clientRequestId` 幂等去重、字段级 LWW（以服务端时间戳为准）+ 冲突队列返回（D-20） |
| **push** | 推送下发 | APNs / FCM / 厂商聚合 SDK 统一发送层，token 路由、到达回执、文案中英双语（D-15） |

基础设施件：
- **PostgreSQL**：主数据存储；`citext`/全文检索用于食物搜索；按 `userId` 索引；迁移用 Prisma 或 TypeORM migration〔假设〕。
- **Redis**：会话/验证码、排行榜（挑战赛 P2）、热配置缓存、限流（sentinel/滑动窗口）。
- **对象存储**：打卡图片与识别图片存 **S3 兼容对象存储**（阿里云 OSS / 腾讯云 COS / MinIO，M0 随云厂商一并定〔待外部确认〕）；客户端直传（STS 临时凭证），后端只存 key；图片经 CDN + 审核回调后可见。
- **队列**：审核、推送、聚合任务走消息队列（BullMQ 基于 Redis）〔假设〕。

### 4.2 部署形态

- **Docker 容器化 + Kubernetes 或云托管（ACK/TKE 或托管 K8s）〔假设〕**；无状态服务多副本，HPA 按 CPU/QPS 伸缩。
- 环境隔离：dev / staging / prod 三套（见第六章），数据库按环境独立。
- 可观测：Prometheus + Grafana 指标、结构化日志（pino）+ 集中采集、OpenTelemetry 链路〔假设〕。
- 数据合规：健康数据境内存储（D-18，PIPL），备份加密，删除请求级联清除（含对象存储与备份策略说明）。

## 五、构建与发布

### 5.1 CI/CD

- **平台：GitHub Actions 或 Codemagic，M0 定〔假设〕**（二选一；若代码托管在 GitHub 且需 iOS 构建机，Codemagic 免去自维护 macOS runner）。
- 流水线（PR）：`flutter analyze`（零告警门禁）→ `dart format --set-exit-if-changed` → domain 单测 + widget 测试（覆盖率 domain ≥90%〔假设〕）→ 构建 Android APK（快速验证）。
- 流水线（发版）：双端构建（iOS `.ipa` / Android `.aab`）→ 上传分发（TestFlight / 国内灰度渠道）→ Sentry 上传符号表/dSYM → 打 tag。
- 后端流水线：lint → 单测 → 镜像构建 → 部署 staging → 冒烟 → 手动审批上 prod。

### 5.2 签名与证书管理

| 端 | 内容 | 管理方式 |
|----|------|----------|
| iOS | 开发者证书、Distribution 证书、Provisioning Profile、App Groups/Push 能力配置 | **fastlane match**（证书/描述文件存加密私有仓库，团队共享）〔假设〕；密钥库密码存 CI Secret |
| Android | upload keystore（`.jks`） | keystore 文件加密存 CI Secret / 密码管理器；**启用 Play App Signing**（Google 托管应用签名密钥）〔假设〕；国内商店上架用同一 keystore 签名 |
| 服务端 | API 密钥、推送证书（APNs Auth Key .p8）、厂商通道密钥 | 环境变量 + 密钥管理服务（云 KMS / Vault）〔假设〕，禁止入库入仓 |

### 5.3 渠道

- **iOS**：App Store 中国区（MVP）；Sign in with Apple 为强制项（D-13）；海外上架待 GDPR 评估（D-18）。
- **Android 国内**：各厂商商店（华为/小米/OPPO/vivo/应用宝等）逐渠道提审〔假设渠道清单〕，包体按渠道打 flavor 以便统计。
- **Google Play**：后续随英文版海外上架评估（V1.1+，D-13/D-15）。
- 灰度发布：iOS TestFlight 内测 → App Store 分阶段发布（Phased Release）；Android 商店灰度比例发布 + Firebase/厂商灰度能力；后端功能用 Feature Flag（配置中心）控制，M4 信号灯等受背书 Gate 约束的功能默认关闭。

### 5.4 崩溃监控与质量

- **崩溃监控：Sentry 或 Crashlytics 选一〔假设〕**——建议 Sentry（前后端统一、Flutter 支持完善、可自托管满足合规），M0 拍板；release 全量接入，符号表随 CI 上传。
- 埋点：按 D-01 口径（WAU-Active、引导完成率、记录 ≤15 秒等）统一埋点规范，埋点 SDK 选型 M0 定〔待外部确认〕。
- 告警：崩溃率、ANR、接口 5xx 接入值班告警通道〔假设〕。

## 六、环境划分

| 环境 | 用途 | 客户端 | 后端 | 数据 |
|------|------|--------|------|------|
| **dev** | 日常开发/自测 | `main_dev.dart`，连 dev API，开启日志拦截器，应用名/图标加 dev 角标 | dev 命名空间，自动部署 main 分支 | 独立库，可随时重置造数 |
| **staging** | 提测/验收/灰度前回归 | `main_staging.dart`，连 staging API，包名带 `.staging` 后缀可与 prod 共存 | 独立部署，发版前手动同步 prod 配置 | 独立库，定期匿名化同步 prod 结构 |
| **prod** | 线上 | `main_prod.dart`，关闭调试日志，Sentry 全量 | 多副本 + HPA，手动审批发布 | 生产库，备份 + 加密 |

实现约定：
- 客户端经 `--dart-define=ENV=xxx` 注入环境（API baseURL、Sentry DSN、推送环境），禁止代码内 if-else 硬编码环境地址。
- 三环境推送证书、对象存储桶、第三方 SDK key 全部隔离。
- staging 是验收唯一环境：PRD 验收标准（含记录 ≤15 秒埋点验收、断食状态机边界用例）在 staging 完成验收后方可上 prod。

## 七、工程规范

### 7.1 分支模型

采用 **trunk-based development**（单主干 + 短生命周期特性分支）：

| 规则 | 内容 |
|------|------|
| 主干 | `main` 永远可发布，受保护（禁止直推，必须 PR + CI 绿 + ≥1 Review） |
| 特性分支 | `feat/<scope>-<简述>` / `fix/<scope>-<简述>`，生命周期 ≤3 天，完成即合入 |
| 发布 | 从 `main` 打 tag（`v1.0.0+build`）；热修复走 `hotfix/<issue>` 分支合回 main 并补 tag |
| 大功能 | 未完成模块用 Feature Flag 隐藏，允许半成品代码合入主干但不允许半成品功能暴露 |

### 7.2 代码评审

- 所有合入必须经 PR Review ≥1 人；domain 层规则引擎（TDEE/阈值/状态机/streak）与同步引擎改动必须双人评审。
- PR 模板含：关联需求/决策编号（如 D-07）、自测说明、状态迁移/边界用例影响、截图（UI 改动）。
- 评审重点清单：UTC/时区处理正确性（D-07）、i18n 无硬编码（D-15）、无障碍三重编码与语义标签（M8）、四态持久化完整性（D-20）、密钥不落明文（D-18）。

### 7.3 Flutter 分析规则（`analysis_options.yaml`）

| 规则类别 | 要求 |
|----------|------|
| 基础 | 继承 `flutter_lints`（或 `very_good_analysis`〔假设〕），`flutter analyze` **零告警为 CI 门禁** |
| 强制 | `always_declare_return_types`、`avoid_dynamic_calls`（network 层白名单豁免）、`require_trailing_commas`、`prefer_single_quotes`、`unawaited_futures`（防同步任务漏 await） |
| 自定义 | 禁止 presentation 层直接 import `dio`/`drift`（自定义 lint 或 import 约束检查）〔假设：经 dart_code_metrics 或自定义 plugin 实现〕；禁止 UI 层硬编码中文字符串（i18n 检查脚本） |
| 格式化 | `dart format` 行宽 80（默认），CI 校验 |

### 7.4 提交信息规范（Conventional Commits）

```
<type>(<scope>): <subject>          # 例：feat(fasting): 断食状态机跨午夜归属日计算 (D-07)
```

| 项 | 规则 |
|----|------|
| type | `feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `perf` / `ci` |
| scope | 模块名：`fasting` / `record` / `nutrition` / `social` / `account` / `sync` / `infra` / `server` 等 |
| 关联 | 涉及决策的实现须在 body 标注决策编号（D-XX）；关联 issue 用 `Refs #123` |
| 语言 | subject 用中文或英文均可，与仓库既有风格统一〔假设：中文团队，subject 用中文〕 |
| 校验 | commitlint + commit-msg hook（或 CI 检查）〔假设〕 |

### A.2 中文路径与环境问题（已全部修复）
